graph 引擎的 SOP

一次 GraphEngine.run() 的标准作业流程 —— 九步一条环，其中两处顺序是承重的。

九步

①
数轮数
进 while 前先 step += 1。计数在动作之前，所以 step 永远等于"已进行的轮数"，掉出循环时它正好是 max_steps。
②
盖脚印必须在 ⑤ 之前
state["current_node"] = current。节点和 router 都只拿得到 state、拿不到 current，所以这个键是它们唯一知道"自己是谁"的途径。
③
visits+1
按节点累加。这是护栏一的账本，和全局的 max_steps 分开记。
④
查护栏一必须在 ⑤ 之前
if visits[current] > max_visits: 返回失败。先判越界，再执行 —— 所以"第 2 次访问被拦下"时，节点实际只跑过 1 次。
⑤
跑节点
patch = nodes[current](state)。读整块板，只返回自己要加的那几行。
⑥
合并
state.update(patch)。合并前先查键碰撞 —— 同一个键被两个节点写过就报错，这是给并行留的。
⑦
问 router
nxt = router(state)。它不接收 current，只能读板上已经写下的东西。这一句就是 graph 和 loop 的全部分歧。
⑧
None 就收工
if nxt is None: return ok。对应 loop 的 end_turn —— 但决定权在代码手里，不在模型手里。
⑨
换 current
current = nxt，然后回 ①。这一句是整张图唯一的回边 —— 也是 A→B→A 那种图存在的唯一原因。
掉出 while 只有一种情况：④ 和 ⑧ 都没拦住，step 用满。这条出口报 max_steps，不能报成 max_visits。

两处承重

② 挪到 ⑤ 后面，节点就成了瞎子

节点想写"我这次干了什么"时读不到 current_node，router 更读不到。后果不是报错，是悄悄走错边 —— 同一张图每次都走同一条路，看起来"能跑"，其实 router 在猜。

④ 挪到 ⑤ 后面，护栏就变成了事后通知

节点会先执行完第 4 次，再被告知"你超了"。对纯函数无所谓，对带副作用的节点就是多做了一次不该做的事 —— 和 loop 里那个孤儿副作用同一类病。
