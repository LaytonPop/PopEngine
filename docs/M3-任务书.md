## 〇、这份文件怎么用

M2 任务书是"照着做"的清单。M3 不一样 —— M3 的核心不是加功能，是**验证一个判断**：

> graph 的价值在"什么时候结束由结构说了算，不由模型说了算"。

所以这份文件的分段不是"第 1 天做什么、第 2 天做什么"，而是**五个必须先钉住的东西**。
每一段都有一个「检查点」问题，答不上来就别往下走 —— 答不上来说明形状还没定。

## 一、靶子与判据（钉死的，别改）

### 靶子

沿用 M2 那个任务，不换：

```text
输入：一个仓库路径
工具：list_dir / read_file
输出：固定 JSON（name / one_liner / language / top_dirs / entrypoints）
```

**不换任务的理由**：换了就不知道数字的变化是引擎差异还是任务差异。M3 只有这一个自变量。

### 判据

**graph 的判据是"更可预测"，不是"更快"。**

这句话是整个 M3 的地基。它决定了实验怎么设计 —— 见第七节，
那里有一个它带来的硬要求（跑一遍不够）。

### 三个指标（不许加第四个）

| 指标 | 从哪来 | 什么意思 |
| --- | --- | --- |
| `model_calls` | `kind == "model"` 的事件条数 | 模型被调用几次，**最重要** |
| `total_ms` | 所有事件 `duration_ms` 之和 | 总耗时（见第六节的口径陷阱） |
| `steps` | 见第七节 —— **这个还没定** | |

## 三、第 1 段：把三个指标从事件里算出来（约 30 分钟）

这一段的产物是一个**纯函数**，不是脚本。理由：纯函数好测。

### 先验算一遍（我已经跑过了，你复核）

`docs/evidence/m2-run-ok.jsonl`，26 行：

```text
kind 分布    model 6 · tool_start 10 · tool_end 10
model_calls  6
总耗时       25644.21 ms
  ├ 等模型   25630.34 ms   ← 99.94%
  └ 跑工具      13.87 ms
```

**这个比例就是"`model_calls` 最重要"的全部论据。** 工具那 10 次调用加起来
不到 14 毫秒，模型 6 次调用吃掉 25.6 秒。想省时间只有一条路：少问模型。

> 记下来，M4 讲稿要用这个数。它不是估算，是 `m2-run-ok.jsonl` 里读出来的。

### 代码怎么写

放 `src/pop_engine/metrics.py`（新文件，不进 loop 的依赖链）：

```python
def summarize(events: Sequence[StepEvent]) -> dict[str, float]:
    """从事件算三个对比指标。

    纯函数：不读文件、不打印、不认识 jsonl。
    """
```

三个实现要点，一条一条来：

1. **`model_calls` 用 `kind == "model"` 数，不要数总行数。**
   M2 里有过一次错：拿"文件行数 == steps"当判据，一旦有工具事件就永远不对。

2. **`total_ms` 是各事件 `duration_ms` 之和，不是墙上时钟。**
   两者在串行执行下近似相等，但含义不同 —— 前者不含 Python 开销。
   **一个 run 只能选一种口径并写明白**，别在报告里混用两种。

3. **`duration_ms` 可能是 `None`**（`tool_start` 没有耗时）。
   用 `e.duration_ms or 0`，不要 `e.duration_ms + ...`。

### 检查点

> **这三个数字，能不能只用 `RunResult.events` 算出来，完全不碰 `messages`？**

必须能。算不出来说明事件埋少了 —— 那是 M2 的洞，现在补比重写便宜。

## 四、第 2 段：先定 graph 的数据形状（不写实现，约 40 分钟）

顺序很重要：**先定形状，再写执行器。** 反过来会写成一坨没人看得懂的东西。

### 三个签名

```python
NodeFn = Callable[[dict[str, Any]], dict[str, Any]]
RouterFn = Callable[[dict[str, Any]], str | None]
```

- `NodeFn` 读**整个** state，返回**要合并的键**（不是返回新 state）
- `RouterFn` 读 state，返回下一个节点 id；`None` 表示收工

### 四条不变量（写进 docstring，不是写进注释）

1. **state 是普通 dict。** 不做 State 类 —— 类会给"能存什么"设上限，
   而黑板的好处正是没有上限。
2. **节点返回的键要不相交。** 串行执行时撞不上，但这条是给将来并行留的。
   现在就在合并处加断言：如果同一个键被两个节点写过，报错说清是哪个。
3. **router 是普通函数，不是 LLM 调用。** 模型写 state，代码读 state 选边。
   这一条是 graph 和 loop 最本质的区别 —— **别让 router 去问模型**，
   那样 graph 就退化成"带名字的 loop"，对比也就没意义了。
4. **`max_visits` 按节点计数，`max_steps` 全局计数。** 两个护栏，别合并成一个。

### 为什么不加第八个原子

`State` 不是一个新类型 —— 它就是 `dict`。
判据（`分层与边界.md`）：**是数据的才当原子，有行为的都是变换器。**
`dict` 已经是内置类型，再包一个 `State` 类只是换个名字，不增加信息。

真要加原子的话，得先回答"加上它之后，什么变得可以表达了"。
答不上来就是装饰。

### 检查点

> **这个 graph 跑完之后，能不能交出一个和 `AgentLoop.run()` 一样的 `RunResult`？**

能，脚本就不用改；不能，你就得写两个脚本、两套输出格式，
然后花时间对齐它们 —— 那是白干的活。

## 五、第 3 段：执行器（约 90 分钟）

### 形状

```python
class GraphEngine:
    def __init__(
        self,
        nodes: Mapping[str, NodeFn],
        router: RouterFn,
        *,
        entry: str,
        max_steps: int = 8,
        max_visits: int = 3,
    ) -> None: ...

    def run(self, prompt: str) -> RunResult: ...
```

和 `AgentLoop` 一样：进 prompt，出 `RunResult`。
**构造器里放配置，`run()` 里放运行状态** —— 和 loop 同一条规矩，别例外。

### 执行循环（伪代码，不是代码）

```text
state = {"prompt": prompt}
current = entry
step = 0
while step < max_steps:
    step += 1
    visits[current] += 1
    if visits[current] > max_visits:  → 失败，error 里说清"哪个节点被访问了几次"
    patch = nodes[current](state)
    state.update(patch)
    nxt = router(state)
    if nxt is None: → 成功
    current = nxt
→ 掉出 while：失败，max_steps
```

### 三个坑，按顺序踩

**坑 1：`agent_node` 怎么复用 loop。**
graph 里总要有节点干真活。那个节点内部调 `AgentLoop.run()`，这是
waku 那句"图包裹循环，从不替代它"。

但它带来一个必须处理的问题：**子 run 的 `events` 怎么并进父 run？**

`StepEvent.step` 的定义是"第几次模型调用（1-based）"（见 `types.py`）。
子 run 的 step 从 1 开始，父 run 也有自己的步数 —— 两套编号会撞。

三个选项，选一个并写进 docstring：

| 做法 | 代价 |
| --- | --- |
| 父 events 只记 router / 节点边界，不记子 run 的 | `model_calls` 就数不出来了 |
| 子 run 的 step 加偏移，拼进父 events | 需要"每个节点起了几次模型调用"的账 |
| 给 `StepEvent` 加 `node: str \| None` 字段 | 改原子（`types.py` 是契约，要说明理由） |

**我的意见是第二个**：不加字段、不改类型，靠"全局 step 偏移"解决。
但这只是意见 —— 你敲代码时觉得别扭，就换，换完把理由写进 docstring。

**坑 2：`max_steps` 和 `max_visits` 会互相掩盖。**
节点 A 被访问 3 次（刚好到 `max_visits`）和全局走了 8 步，哪个先到？
不确定的话，报错信息会指向错误的原因，你会去查错的护栏。

**处理**：两个护栏各自记账，谁先触发就在 `error` 里写明是谁。
别写"超过限制" —— 要写"节点 `scan` 被访问 4 次，上限 3"。

**坑 3：`RunResult.messages` 该放什么。**
loop 的 `messages` 是完整对话现场。graph 的 state 里有多个子 run 的现场。

**处理**：放**最后一次**跑的那个子 run 的 messages。
理由：出问题时人先看最后一步。中间那些留给 events。

### 检查点

> **把 `max_visits` 设成 1，跑一个必然回退的图（A→B→A），报错里有没有说清
> 「哪个节点被访问了几次」？**

说不清就是反向验收过不了。这条在 `验收手册.md` d 轮已经写了，别漏。

## 六、第 4 段：跑对比（约 40 分钟 + 跑的时间）

### 口径陷阱（先看这个再看数字）

`total_ms` 有两种算法，差别不小：

- **A. 各事件耗时之和** —— 不含 Python 开销，比真实快
- **B. 墙上时钟**（`time.perf_counter()` 前后取差）—— 含全部开销

**同一个 run 里必须只用一种。** 报告里两个引擎都用同一种，
并在表下面写明是哪一种。混用会让 `total_ms` 那一列失去意义。

### 表长什么样

```text
| 引擎  | model_calls | total_ms | steps |
| loop  |      ?      |    ?     |   ?   |
| graph |      ?      |    ?     |   ?   |
```

**填不满就别发表。** 三列必须都有数，缺一列说明前面的段没做完。

### 检查点

> **这两行数字，能不能解释清楚"为什么差这么多"？**

不能解释的差异，等于是噪声。可能是任务太简单（模型怎么走都对），
也可能是两个引擎其实在做不同的事。

## 七、两件必须先定的事（动笔前）

这两条不定，后面全是返工。

### 一、`steps` 在 graph 里是什么？

**问题**：`RunResult.steps` 的定义是"调用了几次模型"（`types.py` 原文）。
而 loop 里 **`steps` 恒等于 `model_calls`** —— 每个 step 恰好一次模型调用。

所以三列表里，loop 那行的第一列和第三列**永远是同一个数**。
第三列在 loop 上没有任何新信息。

三个选项：

| 选项 | 结果 |
| --- | --- |
| graph 的 `steps` 也按"模型调用次数"算 | 两行第三列都是 `model_calls` 的别名，**这一列等于没写** |
| graph 的 `steps` = 节点执行次数 | 有意义了，但和 loop 的 `steps` 不是同一个东西，**同名不同义** |
| 删掉 `steps` 这一列，只留两个 | 最诚实，但 `RunResult.steps` 就没被用上 |

**我的意见：第二个，但在表头写清楚两个 `steps` 各自的定义。**
graph 的 `steps` = "结构做决策的次数"（节点执行次数），
loop 的 `steps` = "模型做决策的次数"。这两个数字放在一起才有话说：
**同样的任务，谁做了更多次决策？**

这是必须你拍板的一条，因为它决定 `RunResult.steps` 在 graph 里怎么填。

### 二、"更可预测"怎么测？

**问题**：判据是"更可预测"，但跑一遍看不出可预测性。
一个数字没有方差。

**最低要求：每个引擎跑 3 次，报 `model_calls` 的分布**（3 个数字 + 是否相同）。

如果时间允许，跑 5 次。8 次更好但没必要 —— 这是学习项目，
不是论文实验，3 次能看出"稳不稳"就够了。

**要报什么**：

```text
loop  model_calls: 6, 7, 6      → 会飘
graph model_calls: 6, 6, 6      → 稳
```

这才是"更可预测"的证据。**一次跑出来的相同数字，不能证明可预测**，只能证明巧合。

## 八、会踩的坑

- **别让 router 问模型。** 一问，graph 就退化成带名字的 loop，整个实验失去意义。
- **别为了"更好看"给 graph 加并行**。TODO 里写过了：M3 要回答结构差异，不是并发能力，并行会污染统计口径。
- **别在 `loop.py` 里加 `if`**。想加的先记进 TODO 的 M5。
- **`max_steps` 撞线那步的孤儿副作用**（`test_l`）在 graph 里同样存在。
  如果 graph 也调 loop，这个行为会原样复现 —— 报数字时别把它当新发现。
- **任务太简单可能让两行数字一样。** 一样不是失败，是结论：
  "在这个复杂度下，graph 的结构优势体现不出来"。照实写，别调任务去凑差异。
