# 认知底座：六个洞 · 三原子 · 三板斧 · 七架构

> 这份笔记是 PopEngine 的**词汇表**：它回答「这是什么东西、补哪一格」。
> 它**不回答时间问题** —— 那需要另一份「一次运行的时序」，尚未落纸（见 §一）。
>
> 原稿是 `html/` 下六份 HTML（Pop 自己的总结稿），本文是它们的摘要。
> **只做排版，不动结论。** 细节与原文一律以 HTML 为准。

## 一、为什么还缺一层

我自己的项目口号是「一个我自己写得出来、每行都能解释的 agent 引擎」。但"每行都能解释"这句话，现在的解释方式是有偏的 —— **所有的解释都是名词性的**：

| 这套东西 | 它在回答什么 | 属于哪一类 |
| --- | --- | --- |
| 六个洞 | 六种不可靠法 | **分类学** |
| 七架构 | 在洞之间搬家（补一个、欠一个） | **拓扑学** |
| 三原子 | 环境 / 动作集 / 决策器 | **结构学** |
| 三板斧 | 定位、可测化、假设多强 | **提问法** |
| 五块 | 横向执行管道 | **分层学** |

这五样加起来，能回答「这是什么东西、补哪一格」。但回答不了：

> **在一次运行里，它在第几毫秒发生、它读的是哪一份状态、它写完之后世界变成什么样。**

这个墙其实已经撞到了 —— [`seven-architectures.html`](html/seven-architectures.html) §D 里那句：

> **六个洞里，只有一个从没当过任何一种架构的设计目标：③ 看不见。**

为什么没人拿它当目标？因为"看不见"不是一次**决策**，是一次**运行里的观测缺失**。
分类学看不见时间，所以它天然没法把"看不见"当成一格来设计。

**所以：呈现一个运行一次的状态，就是给这套分类学补上时间轴。**

时间轴那一半（一次 run 里每个可观测时刻、每个时刻被 kill 留下什么）**还没写**。
判据先记在这里：**表里每一行，要么对应一条测试，要么对应一处代码注释；对不上的删掉。**

## 二、六个洞：现代技术全是补丁

决策器不可靠，只有六种不可靠法。所有技术都在补其中一格。

| 洞 | 症状 | 补它的技术 |
| --- | --- | --- |
| **① 不知道** | 凭空编 | 上下文工程、RAG、记忆 |
| **② 做不对** | 参数错、格式错、选错工具 | 工具设计、schema、few-shot |
| **③ 看不见** | 出错不知为何 | trace、事件、评估 |
| **④ 停不下** | 无限循环、预算爆 | 预算、停止判据、护栏 |
| **⑤ 收不回** | 文件删了、消息发了 | 权限、幂等、沙箱、人工确认 |
| **⑥ 想不过来** | 一个上下文装不下 | 多 Agent、编排、分工 |

这张表就是地图。看到任何新框架、新论文，先问一句：**它补的是哪一格？**
答得出来，你就有判断力；答不出来，说明还没读懂它。

> 出处：[`agent-first-principles.html`](html/agent-first-principles.html) §E

## 三、三原子

把 Agent 剥到底，剩一个循环：

```text
环境 ──感知──> 决策器 ──动作──> 环境
```

- **环境**：它能看见什么、能改什么。
- **动作集**：它一共能做什么。
- **决策器**：它凭什么选这一个，而不是那一个。

其余的一切，都是这三样的推论。

> 出处：[`agent-first-principles.html`](html/agent-first-principles.html) §B

## 四、提问三板斧

堵住人的不是理解力，是词汇表。有了上面那张表，任何东西都能问三句：

1. **它补哪个洞？** 定位它属于哪一格。
2. **它把哪个「不可靠」变成了「可测」？** 只让结果变好不算解决，只算缓解。
3. **它假设决策器有多强？** 换成弱模型还成立吗？

第三句最狠 —— 它专门用来认「写给 GPT-4 的情书」。

> 出处：[`agent-first-principles.html`](html/agent-first-principles.html) §F

## 五、七个架构

先说清两个词，否则面试会被追问：

- **架构** = 组织方式：谁决定下一步、能力怎么分、流程谁保证。
- **框架** = 承载它的代码库：LangGraph、Temporal、n8n、Dify。

那四篇文章讲的是**架构**。说成「七个框架」，面试官就会问"你用哪个库"。

### 5.1 三组

```text
七种架构
  第一组 决策：谁决定下一步
    Single Agent     一步答完
    ReAct            每圈重问
    Plan & Execute   计划先定
  第二组 组织：能力怎么分配
    Multi-Agent      谁来做
    Router + Skill   用哪套方法做
    Blackboard       围着共享状态写
  第三组 控制：流程谁保证
    Graph / Workflow 边由代码定
```

### 5.2 主表：补齐一个，再欠一个

不是七对六。**七种是七次搬家** —— 补一个洞的同时新欠一个洞。

| 架构 | 补哪个洞 | 新欠哪个洞 |
| --- | --- | --- |
| Single Agent | 无。它是零点 | 六个全欠 |
| ReAct | ① 不知道 | ④ 停不下 · ② 做不对 |
| Plan & Execute | ⑥ 想不过来（长任务） | ② 做不对（计划错到底） |
| Multi-Agent | ⑥ 想不过来（窗口变窄） | ③ 看不见 · ⑤ 收不回 |
| Router + Skill | ② 做不对 | ① 不知道（覆盖不全） |
| Blackboard | ⑥ 想不过来（共享状态） | ③ 看不见（状态难追） |
| Graph / Workflow | ④ 停不下 · ⑤ 收不回 · ③ 审计 | ① 不知道（图外无出口） |

原文对 Multi-Agent 有一句纠正：它解决的是**专业分工**，不是任务复杂度。
别把它理解成「任务太难，所以多拆几个」。
