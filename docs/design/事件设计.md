## 〇、先纠正一句错话：「说完就扔了」不准确

这句话把三件不同的事混成了一件。查过代码之后，五个字段各自的状态是：

| 字段 | 真实状态 | 该怎么说 |
| --- | --- | --- |
| `duration`（耗时） | **全仓零计时代码**，`time` / `perf_counter` 一次都没出现过 | **从来没测过** —— 不是扔了，是根本不存在 |
| `is_error` | `ToolResult.is_error` 有值，但 `loop.py` 只读 `result.content` 和 `result.tool_call_id`，**从来没读过它** | **造出来了，从没被取用** |
| `step` | `for step in range(...)` 的循环变量，`steps=` 传进 `RunResult` | 读过、用过一个整数，**但每一步是第几步没有留痕** |
| `stop_reason` | `response.stop_reason`，三个 `if` 都用它分支 | 读过，**值本身没留下来** |
| 工具名 | `Message(name=call.name)` | **其实留下了** —— 但留在了 `messages` 里，那是给模型看的上下文，不是给人看的记录 |

所以准确的三种情况是：

1. **从未测量**（耗时）—— 连值都不存在
2. **有值但从未读取**（`is_error`）—— 对象造好了，没人伸手去拿
3. **读过但没留**（`step`、`stop_reason`）—— 参与了判断，判断完就散

这三种在工程上是三个不同的问题，修法也不同：
第 1 种要**加埋点**，第 2 种要**改取值路径**，第 3 种要**加一个容器**。

> 这件事本身值得记：讲"可观测性"的时候，说"日志不够"很空；
> 说"我有三个字段，一个没测、一个没读、一个没留"，是具体的。

## 一、边界：事件属于 loop，序列化属于脚本

这是本轮唯一的设计决定，其它都是从它推出来的。

```
loop.py        产出 StepEvent 对象        不认识 JSON、不认识文件、不认识路径
run_task.py    把 StepEvent 写成 jsonl    不认识 loop 内部怎么跑的
```

**为什么序列化必须在脚本里**：`events.jsonl` 只是一种形态。将来要 stdout、要 SQLite、
要发到远端，改的都是消费方。如果让 `loop.py` 直接 `open()` 写文件，engine 就绑死了
"JSONL 文件"这一种形态 —— 那才是真的耦合。

**为什么事件本身必须由 loop 产出**：这五个信息只有 loop 在手上，脚本无论怎么写都拿不到
（见上面第 2 行的 `is_error`：它连读都没读，脚本更没有机会）。

一句话：**loop 负责"发生了什么"，脚本负责"怎么记下来"。**

## 二、数据模型：`StepEvent`

加在 `src/pop_engine/types.py`，和其它数据类放一起（这个文件"刻意不含任何行为"）。

```python
EventKind = Literal["model", "tool_start", "tool_end"]


@dataclass(frozen=True)
class StepEvent:
    """一次 run 里发生的单件事。**给人看的，模型永远看不到它。**

    和 Message 的分工：
      - Message 是模型视角的对话上下文，下一轮 chat 要用它
      - StepEvent 是人的视角的观测记录，只用来调试和做 M3 的对比
    两者都放在 RunResult 里，但消费方不同 —— 这个区分比字段本身重要。
    """

    kind: EventKind
    step: int  # 第几次模型调用（1-based）

    # kind == "model" 时有意义
    stop_reason: LLMStopReason | None = None
    duration_ms: float | None = None  # 这次 chat 调用花了多久

    # kind 是 tool_* 时有意义
    tool_name: str | None = None
    tool_call_id: str | None = None
    is_error: bool | None = None

    # 失败时填（provider 抛异常、参数坏掉等）
    error: str | None = None
```

### 为什么是一个类 + `kind`，不是三个类

字段少（8 个），一个类写起来、读起来、序列化都简单；`kind` 就是判别式。
**这是一处明确的取舍**：如果事件种类涨到五六种、字段开始互斥得厉害，就该拆成 Union。
现在拆是过度设计。面试被问"为什么用一个类"，答案是"字段还没多到值得拆"。

### `RunResult` 只加一个字段

```python
@dataclass(frozen=True)
class RunResult:
    ...
    error: str | None = None
    events: tuple[StepEvent, ...] = field(default_factory=tuple)  # ← 新增
```

需要把 `types.py` 顶部改成 `from dataclasses import dataclass, field`。

**必须用 `field(default_factory=tuple)`，不能写 `= ()`**：虽然 tuple 不可变、写 `()` 也不会出错，
但一旦哪天换成 list/dict，`= []` 就是经典的共享可变默认值坑。现在养成习惯，比将来踩一脚便宜。

**这是个纯增量改动**：`loop.py` 现有的 4 个 `RunResult(...)` 一个都不用动，
测试也一条都不会红 —— 因为它们不传 `events`，拿到默认的空 tuple。

### 2. `src/pop_engine/loop.py`

顶部加 `import time`。

`run()` 里四件事：

**① 开一个容器，放在 `tool_specs` 旁边**

```python
tool_specs = self.tools.specs()
events: list[StepEvent] = []
```

**② 每次 chat 前后计时，无论成败都记一条 `model` 事件**

```python
for step in range(1, self.max_steps + 1):
    started = time.perf_counter()
    try:
        response = self.provider.chat(list(messages), tool_specs)
    except Exception as exc:
        events.append(
            StepEvent(
                kind="model",
                step=step,
                duration_ms=_elapsed_ms(started),
                error=f"{type(exc).__name__}:{exc}",
            )
        )
        return RunResult(..., events=tuple(events))

    events.append(
        StepEvent(
            kind="model",
            step=step,
            stop_reason=response.stop_reason,
            duration_ms=_elapsed_ms(started),
        )
    )
```

**③ 每个工具调用发 `start` / `end` 两条**

```python
for call in response.message.tool_calls:
    events.append(
        StepEvent(kind="tool_start", step=step, tool_name=call.name, tool_call_id=call.id)
    )
    started = time.perf_counter()
    result = self.tools.invoke(call)
    events.append(
        StepEvent(
            kind="tool_end",
            step=step,
            tool_name=call.name,
            tool_call_id=result.tool_call_id,
            is_error=result.is_error,
            duration_ms=_elapsed_ms(started),
        )
    )
    messages.append(Message(...))  # 原样不动
```

> **为什么两条而不是一条**：`验收手册` c 轮通过标准第 2 条要求"每次工具调用有 start / end 两条"。
> 这个引擎没有流式、没有异步，一个工具调用中途不可能被观察到，所以**两条在观测上没有额外价值**。
> 但它能满足手册的判据，也能让"开始但没有结束"这件事在日志里显形（比如进程被 kill）。
> **如果嫌冗余想合成一条：可以，但必须同时改进手册第 2 条** —— 不要代码悄悄变了、判据还写着旧的。

**④ 四个出口都带上 `events`**

`end_turn`、`unknown`、异常、`max_steps`，四个 `RunResult(...)` 各加 `events=tuple(events)`。

顺带把 `max_steps` 那个出口的 `error` 从 `None` 改成人话（`M2-待办.md` 第 3 条）：

```python
error=f"超过 max_steps={self.max_steps} 步仍未结束",
```

**这个改动是安全的**：查过 `tests/test_loop.py`，`test_c_stop_at_max_steps` 只断言
`status` / `stop_reason` / `steps` / `provider.calls` 和第一条消息的 role，
**没有一条断言 `error is None`**。场景 A 那个 `assert result.error is None` 走的是 `end_turn` 出口，不受影响。

**⑤ 加一个小工具函数**（放在 `AgentLoop` 类外面，模块级）

```python
def _elapsed_ms(started: float) -> float:
    """从 started 到现在经过了多少毫秒，保留两位小数。

    perf_counter 是单调时钟，不受系统时间调整影响 —— 计量必须用它，不能用 time.time()。
    """
    return round((time.perf_counter() - started) * 1000, 2)
```

### 3. `scripts/run_task.py`

这个文件改两处：**参数解析**和**写文件**。

**① `--trace` 从"开关"变成"带路径的参数"**

现在的实现有个静默 bug：

```python
args = [item for item in argv if not item.startswith("--")]   # ← 病根
show_trace = "--trace" in argv
```

`--trace traces\a.jsonl` 传进来，第二个参数不以 `--` 开头，会被当成**仓库路径** ——
于是 `args` 里多了一个 `traces\a.jsonl`，而 `--trace` 依然只是个"打印到终端"的开关。
**跑完 PASS、退出码 0、文件根本没创建。这是最坏的一种失败：静默的。**

2026-11-07 实测：

```
& run_task.py <repo> --trace traces\a.jsonl
→ PASS
→ traces/ 目录根本没被创建
```

改成显式解析：

```python
def parse_args(argv: list[str]) -> tuple[Path, Path | None]:
    """拆出「仓库路径」和「可选的 --trace 输出路径」。

    不用 argparse：这里只有两个参数，而 argparse 会把 --help 的文案也接管过去，
    反而看不清我们自己想说什么。手写一个够用，也更好讲。
    """
    repo: str | None = None
    trace: str | None = None
    i = 0
    while i < len(argv):
        arg = argv[i]
        if arg == "--trace":
            i += 1
            if i >= len(argv):
                raise SystemExit("--trace 后面要跟一个输出路径")
            trace = argv[i]
        elif arg.startswith("--"):
            raise SystemExit(f"不认识的选项：{arg}")
        elif repo is None:
            repo = arg
        else:
            raise SystemExit(f"多余的位置参数：{arg}")
        i += 1

    if repo is None:
        raise SystemExit("用法: python scripts/run_task.py <仓库路径> [--trace <输出路径>]")
    return Path(repo), (Path(trace) if trace else None)
```

**② 写 jsonl**

```python
from dataclasses import asdict   # 顶部

def write_events(path: Path, events: tuple[Any, ...]) -> None:
    """把事件一行一条写成 JSONL。父目录不存在就建。"""
    path.parent.mkdir(parents=True, exist_ok=True)
    with path.open("w", encoding="utf-8") as fh:
        for event in events:
            fh.write(json.dumps(asdict(event), ensure_ascii=False) + "\n")
```

`ensure_ascii=False`：中文原样落盘，不用 `\uXXXX`。这份文件是给人看的。

在 `main()` 里 `result = ...run(...)` 之后：

```python
if trace_path is not None:
    write_events(trace_path, result.events)
    print(f"events   : {trace_path}（{len(result.events)} 行）")
```

**`--trace` 不传路径时**：保持现在的行为（`show_trace` 打印到终端）。
两个功能不冲突：一个是给人当场看的，一个是落盘给程序读的。

## 四、红线：事件里绝不能出现 key

events 的字段是**白名单**，不是黑名单：只有上面那 8 个，一个都不多。

**绝对不要**为了"方便调试"顺手把这些东西塞进去：

- 完整 request body（里面 `Authorization: Bearer sk-...`）
- 任何 header
- `payload`、`messages` 原文、`tools` 原文

这是 c 轮唯一的红线，验收手册里有对应的检查命令：

```powershell
Select-String -Path traces\*.jsonl -Pattern "sk-","Authorization" -SimpleMatch
```

**期望：没有任何输出。**

> 为什么单列一条：事件系统最容易"顺手多记一点"。而记 request body 的诱惑最大 ——
> 出问题的时候你确实最想看它。但那等于把 key 明文写进一个会被提交、会被分享的文件。
> 要记就记**摘要**（模型名、消息条数、工具个数），不要记原文。

### 实现后发现的一条遗漏：`error` 字段是别人写的

上面这条红线管住了**我们主动记什么**，但漏了**被动进来的东西**：
`StepEvent.error` 装的是 `RuntimeError` 的文本，而那段文本里有**服务端返回的原文**。

2026-11-10 用错 key 实测，DeepSeek 自己把 key 脱敏了（回显 `****pose`），所以没出事。
但这**不是我们能保证的** —— 换个服务商若在错误信息里回显完整 key，这个字段就会把 key
写进日志，而字段本身完全合法（它只是 `error: str`）。

所以两件事：

1. **红线检查每次都要跑，不能因为"上次干净"就跳过** —— 它的价值在于捕捉外部变化。
2. **真要治本，位置在 `provider.py`**：抛错前把 key 从 `detail` 里替换掉。
   那是 provider 的责任，因为只有它知道 key 是什么。**不要放到 loop 或序列化层** ——
   它们拿不到 key，硬做只能靠猜正则，那是更糟的耦合。


**四条判据**：

1. **`kind == "model"` 的事件条数 == `RunResult.steps`**，不重不漏
2. **每个工具调用有 `tool_start` / `tool_end` 两条，且两条的 `tool_call_id` 相同**
3. 故意失败那次（错 key）也有一条 `model` 事件，`error` 字段里有状态码
4. 上面那条 `sk-` / `Authorization` 的搜索**无输出**

**总行数应该是**：`steps + 2 × 工具调用次数`

> **这里要跟手册对一下账**：验收手册 c 轮通过标准第 1 条写的是
> "文件行数能和 `RunResult.steps` 对上，不重不漏"。
> 一旦有工具事件，总行数就**不可能**等于 steps。
> 那条判据的正确读法是"**`kind == "model"` 的行数 == steps**"，
> 不是"总行数 == steps"。手册那句要跟着改，别让判据和实现对不上。

**另外建议补三条测试**（`tests/test_loop.py`，接在场景 F 后面）：

- `test_g`：一次 `end_turn` 的 run → `len(events) == 1`，`kind == "model"`、`step == 1`、`stop_reason == "end_turn"`
- `test_h`：一次工具调用 → `kind` 序列是 `["model", "tool_start", "tool_end", "model"]`，两个 tool 事件的 id 相同
- `test_i`：provider 抛异常 → 最后一条事件的 `error` 非空

> `test_h` 的 `kind` 序列断言最值钱：它把"顺序"钉死了。
> 只断言"有两条 tool 事件"的话，"先 end 后 start"这种错误照样绿。

## 六、不做什么（本轮冻结）

- **不引第三方库**：`pyproject.toml` 里 `dependencies = []`，这是这个项目的原则（"不引 openai SDK"就是为了这个）。计时用 `time.perf_counter`，序列化用 `json` + `dataclasses.asdict`，都是标准库。
- **不做日志框架**：不引 `logging`，不搞 handler / formatter / level。原因是**用途不同**：logging 输出给人看的文本流，事件要的是能被程序读取的结构化记录。混在一起，M3 对比时还得再解析一遍文本。
- **不做流式**：事件是"跑完一起交出来"，不是边跑边推。
- **不做采样 / 轮转 / 上报**：文件写满不关我事。
- **不改 `loop.py` 的控制流**：这一轮只加埋点和 `events=` 参数。`if` 的顺序、`return` 的时机一律不动。
  改了就要重跑 a 轮回归（见验收手册 b 轮 ③）。

## 七、改完要能答的三个问题

1. 为什么 `events` 放 `RunResult`，而不是让 loop 直接写文件？——序列化只是一种形态，engine 不该绑死它；反过来，那五个信息只有 loop 手上有，脚本要不出来。
2. `messages` 和 `events` 都在 `RunResult` 里，凭什么一个进一个出？——`messages` 是**模型视角**的上下文（下一轮 chat 要用），`events` 是**人的视角**的观测记录（模型一辈子看不到）。同一个容器，两个消费方。
3. 加 `events` 字段为什么不用重写那 4 个 `RunResult(...)`？——`field(default_factory=tuple)` 给了默认值，是纯增量；老代码不传就拿到空 tuple。这也是"向后兼容"最省的做法：**加可选字段，不改必填字段**。
