# 三层与两轴：`agent = loop + graph + harness` 这句话怎么讲才站得住

> 来源：2026-11-18 Pop 口述的一份整体理解。本文只做三件事：确认它对在哪、
> 标出四处与 `graph.py` 打架的口径、给一版可直接用的叙述（§六）。
> **loop / graph 的分工不在这里重讲**，owner 是 `design/引擎对比.md`；
> **五层不在这里重讲**，owner 是 `design/分层与边界.md`。

---

## 一、结论

三块的分工成立。但 `=` 这个符号不成立 —— 因为 **harness 不在同一根轴上**。

真实结构是**两根轴 + 一个横切面**：

| | 轴一：控制权 | 轴二：抽象层次 |
| --- | --- | --- |
| 回答什么 | 下一步谁说了算 | 站在哪一层看这个系统 |
| 取值 | loop（模型）/ graph（结构） | L0 … L4（见分层与边界） |
| 关系 | **可嵌套**：graph 的节点里可以放 loop | graph 落 L3 |

**harness 不算第三层**，它贯穿两者 —— 这一点 Pop 自己也写了（"横贯所有节点、
所有 Loop 的底层运行围栏"）。既然"横贯"，就不能和另外两块并排相加。

一句话：**轴一有两个取值，轴二是标尺，harness 是一个切面。三者不是加法关系。**

---

## 二、轴一：谁决定「下一步」

这是整个 M3 要验的那个变量。两个取值：

| | loop | graph |
| --- | --- | --- |
| 下一步谁定 | 模型（`stop_reason`） | 结构（`router(state)`，普通函数） |
| 边界在哪 | 一次 run 内，靠预算收口 | 节点之间，靠 `max_visits` + `max_steps` 收口 |
| 代码 | `loop.py` | `graph.py` |

**可嵌套，不可替换。** 嵌套是单向的：graph 的节点里可以调 loop，
loop 里不会调 graph（真要调就是递归，`max_steps` 会兜住但没意义）。

⚠️ 这条嵌套关系在**最小实现里没发生**：`graph.py:37` 的
`NodeFn = Callable[[dict[str, Any]], dict[str, Any]]` —— 节点是个函数，
不是 loop 单元。所以现在这版 graph 里**一个 loop 都没跑过**。
"graph 调度一堆 loop"是设计空间里的用法，不是当前代码的事实。

---

## 三、轴二：五层

只在一点上和本文有关：**graph 在 L3（编排 · 多个 run），loop 在 L1（分子）。**
所以在层数上看，graph 确实在 loop 上面 —— 但"在上面"说的是抽象层次，
不是"graph 管着 loop"。管不管得着，取决于节点里放没放 loop。

见 `design/分层与边界.md` §五。

---

## 四、Harness 不是第三层，是每一层各出一部分

Pop 列的六项能力，逐项对一下现状：

| 能力 | 该落在哪 | 现状 |
| --- | --- | --- |
| 字段强校验 | L0 转换层 | ✅ `from_wire` 已在做（含两条 `raise`） |
| 日志审计 | L1 事件 | ✅ `StepEvent` 已在做 |
| 接口权限 | L2 权限 | ❌ 0 |
| 调用频次限流 | L2 并发 | ❌ 0 |
| 异常熔断 | L2 并发 | ❌ 0 |
| 高危操作拦截 | L2 权限 | ❌ 0 |

**六项里没有一项属于"新的一层"。** 三格已经在做，三格属于 L2 五格里那两格
（权限、并发）—— 而 L2 现在是 0 / 5。

⇒ 想做 harness，不是"新建一个模块"，是**给已经散在各处的检查点起一个统一的名字，
再把缺的三格补上**。这个区别很重要：前者听着像要写很多东西，后者听着像整理。
实际是后者。

## 五、四处口径要改

### ① 「graph 负责调度一堆干活的 Loop」

**改**：graph 调度的是**函数**，不是 Loop。

出处：`graph.py:37` `NodeFn = Callable[[dict[str, Any]], dict[str, Any]]`。

节点签名只有"从 state 读、往 state 写"。里面放 loop 也行、放一次模型调用也行、
放纯计算也行 —— **graph 不知道、也不需要知道。** 这恰恰是 graph 设计得好的证据：
它真不替换 loop，因为它根本不认识 loop。

### ② 「控制流完全显性化，不靠模型脑补」

**只对一半。** 显性化的是**节点之间的转移**；节点内部的判断仍然是模型的。

这条不是推测，是从 Pop 自己写下的第四条不变量推出来的
（`graph.py:16`）：**"router 是普通函数，不许在 router 里问模型 —— 一问，
graph 就退化成'带名字的 loop'"。**

由此可以推出一句比原文准确得多的话：

> **模型还在做判断，但它只判断"事实"，不判断"流程"。**
> 电商那个例子里，"这单符不符合退货条件"由某个节点算出字段写进 state；
> "符不符合 → 去哪个节点"是 router 用代码查表。
> 模型失去了"我该去哪"这个自由度，只剩下"这事实是什么"。

**这就是可预测性的真正来源** —— 不是模型变准了，是它被剥掉了选路的权力。

### ③ 「子任务失败只重跑对应节点」

**需要一个前提，而这个前提正是 M5 的第一问。**

重跑一个节点 = 把节点里的东西再执行一遍。如果节点里放的是 loop，
那里面调过的工具会**再调用一次** —— 副作用执行两遍。

这不是假想：`loop.py` 里已经有这个现场（用满 `max_steps` 的那一步，
工具已执行、结果模型读不到，见 `tests/fakes.py:96` 的注释）。
graph 只是换了个位置出现同一件事。

⇒ 正确表述：**"子任务失败只重跑对应节点"的前提是节点幂等。** 不幂等的时候，
重跑要么带账本去重，要么人工介入。这句话在当前代码里不成立。

### ④ 「断点续跑和流程观测都方便」

**只到节点边界。**

能序列化的是 `state` + `current_node` + `visits` 三样。
序列化不了的是"已经进到节点内部第 3 步"—— 节点是函数，执行到一半的状态在栈上。

⇒ 断点只能落在**节点之间**，落不到节点内部。节点里如果放了 loop，
一个 loop 跑到一半崩了，续跑点在节点入口，不在第 3 步。

这条不是缺陷，是必须提前知道的边界。做 resume 时按这个前提设计，才不会
写着写着发现"续跑"其实是"重跑"。

## 六、修订版叙述（可直接用）

> **Agent 系统 = 两个可嵌套的执行体 + 一个横切围栏。**
>
> **Loop 回答"下一步"。** 过去把 agent 当成一套 prompt 加几个 workflow，
> 它做不了前置规划、不会动态调整、不会自我反思。Loop 就是把这个缺口补上的机制：
> 反复尝试、状态居中、带防护。很多"agent 跑偏"不是模型问题，是这个方面做得不好。
> 它是思考的发动机。
>
> **Graph 回答"我们走到哪了"。** 把流程做成节点加有向边的显式拓扑，
> 把原本藏在模型脑子里的"下一步"改成开发者写下来、能配置的结构。
> 节点可以是 Loop、工具、子 Agent、人工审批；边管条件、依赖、分支、回退、汇聚。
> **所以 Graph 不替换 Loop：它决定了顺序，Loop 决定了每一步做多久。**
> 它补的是流程失控 —— 走哪条边、失败退回哪、哪里人工介入，全在结构里。
>
> 但要说清一处：**Graph 不是让模型不做判断。** 模型还在判断，只是它判断的是
> "事实是什么"，而不是"下一步去哪"。判断事实的活留给节点，选路的权力收进 router。
> **可预测性从这来，不从"模型变准了"来。**
>
> **Harness 回答"谁不许做什么"。** 它不替换任何一块，也不在它们上面：
> 它横贯所有节点、所有 Loop，把字段校验、权限、限流、熔断、审计、高危拦截
> 统一成一个可设计的切面，而不是散在各处的 if。
>
> 一句收尾：**Loop 是发动机，Graph 是变速箱和方向盘，Harness 是刹车和保险带。**
> 三样都装齐了才是车 —— 但它们不在同一个位置上。

## 七、「可预测」怎么写才不是一句空话

本文件全在讲结构，但结构差异**本身证明不了任何事**。M3 定过一个指标口径：
**同任务、同模型，每个引擎跑三次，报 `model_calls` 的分布。**

判据是**方差**，不是均值：graph 的 `model_calls` 应当等于节点数（结构固定），
loop 的则随模型每次的选择浮动。

⚠️ 一个未决问题（Pop 自己提的，暂无答案）：loop 一道护栏（`max_steps`），
graph 两道（`max_visits` + `max_steps`）。**graph 多一道守卫，这个对比算不算公平？**
在 `agent_node` 真跑出数据之前，别编答案。
