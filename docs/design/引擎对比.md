## 一、体量：先摆数字，别拿它当结论

```limits
PopEngine 循环 | 139 | 行

pi 类型定义 | 551 | 行
Claude Code 二进制 | 260 | MB
Codex 二进制 | 319 | MB
```

**别急着从 139 vs 959 推出"我差得远"。**

那 959 行里，属于"循环"的部分只有 `runLoop` 一个函数（约 170 行）。其余全是：


## 二、最硬的一处分歧：`finish_reason=length` 怎么办

这是两份实现**明确对立**的地方，而且我 M2 那个"刻意从严"的取舍，pi 不同意。

### 我的做法【读源码】

```python
if response.stop_reason == "unknown":
    return RunResult(
        status="failed",
        stop_reason="error",
        error=f"模型以未建模的原因停下（stop_reason=unknown），第 {step} 步中止",
        ...
    )
```

`finish_reason=length` 被 `from_wire` 映射成 `unknown`，然后**整轮作废**。

当时的理由写在映射表 §七：

> 截断的调用参数大概率是坏的，执行一个半截动作可能比失败更危险。

### pi 的做法【读源码】

```ts
if (hasMoreToolCalls = false, toolCalls.length > 0) {
    const executedToolBatch =
        message.stopReason === "length"
            ? await failToolCallsFromTruncatedMessage(toolCalls, emit)
            : await executeToolCalls(currentContext, message, config, signal, emit);
    ...
}
```

它的选择是：**这一批调用判为失败，但对话继续。**

模型下一轮会看到"你上次的调用因为输出被截断而失败了"，然后自己重来。

### 两个方案的真正差别

| | 我的 | pi 的 |
| --- | --- | --- |
| 半截参数会不会被执行 | 不会 | 不会（**这点我们一致**） |
| 整轮会不会作废 | **会** | 不会 |
| 代价 | 一个可恢复的问题变成一次 run 失败 | 多花一次模型调用 |

**我的做法没有错，但它是"保守"，不是"最优"。**

pi 的写法要求一件事：模型得能理解"你的调用被截断了"这句话并改正。这需要提示词和模型能力配合。
我的做法假设模型改不了——所以直接放弃。

**M3 之后如果要改，这是第一个该改的点。** 但改之前要有证据：模型真的能自愈吗？

## 三、第二处：停止条件，我只有一个，它有五个钩子

### 我的【读源码】

```python
for step in range(1, self.max_steps + 1):
    ...
return RunResult(status="failed", stop_reason="max_steps",
                error=f"超过 max_steps={self.max_steps} 步仍未结束")
```

**`max_steps=8`，唯一的一条死线。** 拍脑袋定的，我 M2 自己承认过。

### pi 的【读源码】

主循环是 `while (true)` —— **没有步数上限**。它靠这些停：

```ts
export type FinishTurn = (
    turn: AgentTurnContext,
    signal?: AbortSignal,
) => AgentTurnDecision | void | Promise<AgentTurnDecision | undefined> | Promise<void>;
```

外加 `PrepareRequest`、`PrepareNextTurn`、`getSteeringMessages`、`getFollowUpMessages`。

`types.ts` 里那句注释说得很清楚：

> Called after a completed assistant turn and all of its tool-result messages, but before `turn_end`.
> On a normal turn, `{ action: "continue" }` ensures one next provider request.

**这套设计的核心是：把"要不要继续"从循环里搬出去，变成一个回调。**

循环不知道自己为什么停，它只问 `finishTurn` 要一个 `{action: "end"}`。

### 这对我意味着什么

我的 `max_steps` 是**硬编码在循环里的一条规则**。
它的 `finishTurn` 是一个**插槽**，谁都可以往里塞判断：token 预算、重复检测、用户中断、成本上限。

```callout warn 这是整份对比里最该抄的一处
把 `max_steps` 从"循环里的常数"改成"循环外的判断函数"，改动量很小：

    AgentLoop(..., should_stop: Callable[[State], bool] | None = None)

但它的价值不在代码，在**它让"什么时候停"变成了可讨论、可测试、可替换的东西**。
我现在的 8，永远只能是 8。
```

## 四、第三处：工具并发

### 我的【读源码】

```python
for call in response.message.tool_calls:
    result = self.tools.invoke(call)   # 一个接一个
```

串行。模型一次要三个工具，就等三次。

### pi 的【读源码】

两套实现，配置里选：

```ts
export type ToolExecutionMode = "sequential" | "parallel";
```

`executeToolCallsParallel` 的逻辑（节选）：

```ts
for (const toolCall of toolCalls) {
    await emit({ type: "tool_execution_start", toolCallId: toolCall.id, ... });
    const preparation = await prepareToolCall(...);
    if (preparation.kind === "immediate") { /* 直接失败，不占并发 */ }
    finalizedCalls.push(async () => { ... });   // 攒成待执行的闭包
}
```

**先全部准备，再一起执行。** 准备阶段就能失败的（参数不合法、工具不存在）不占并发名额。

### 但这件事有个前提我没做

我的 `list_dir` / `read_file` 是纯读操作，**并发是安全的**。
pi 敢默认并发，是因为它的工具有权限系统和沙箱。

**我要做并发，得先回答：哪些工具能并发？** 答案是"只读的能，会写的不行"。
这个分类现在在我这儿根本不存在。

## 五、第四处：中止（我完全没有）

数字说明一切：

```limits
pi 循环里 abort/signal 出现 | 68 | 次
PopEngine 里同样搜索 | 0 | 次
```

pi 的每个工具执行前都查一次：

```ts
if (signal?.aborted) {
    const finalized = {
        toolCall,
        result: createErrorToolResult("Operation aborted"),
        isError: true,
    };
    await emitToolExecutionEnd(finalized, emit);
    return finalized;
}
```

**我的引擎一旦开始跑，就没有任何办法让它停下来。** 用户 Ctrl+C 只能杀进程，杀掉就等于丢了整个 run 现场。

这不算 bug——M1/M2 的任务书明确把"权限审批"和"流式"冻掉了。
但它是**真实的缺口**，而且是最容易补的一个：一个 `threading.Event` 加几个检查点。

## 六、`length` 之后那个设计差异，其实指向同一件事

把二、三、四、五放在一起看，pi 和我做的其实是两种不同的东西：

| | 我的 | pi 的 |
| --- | --- | --- |
| 循环 | **闭合的类** | **带插槽的壳** |
| 谁决定继续 | 循环自己（`max_steps`） | 外部回调（`finishTurn`） |
| 谁决定并发 | 没得选 | 配置 |
| 谁能中止 | 没人 | `AbortSignal` |
| 谁能改上下文 | 没人 | `prepareRequest` / `prepareNextTurn` |

一句话：**我的循环是一个函数，它的循环是一个协议。**

这也解释了我 M2 那个困惑——"为什么 Claude Code 要 260MB"。
不是循环复杂，是**它把循环周围所有能插东西的地方都留成了插槽**，然后往每个插槽里塞了实现。

## 七、M3 该怎么做（这份文件的用途）

既然 M3 要完整实现 graph，那**graph 不该是"另一个 loop"，而该是"另一个 `finishTurn`"**。

具体三条：

1. **先把"什么时候停"变成可讨论、可测试的东西。** 原话是"把 `should_stop` 抽出来"，
   2026-11-12 经过一次反驳后**降到第一档：先写行为，不先抽函数**（见本节后面的补记）。

2. **对比指标定死三个，不要更多。**
   - `model_calls`（模型被调用几次）← **最重要的，因为时间全花在这**
   - `total_ms`（总耗时）
   - `steps`（步数）

   有了 c 轮的事件系统，这三个数字都是现成的。

3. **graph 的判据不是"更快"，是"更可预测"。**
   我在别处说过一句猜测：graph 的价值在"什么时候结束由结构说了算，不由模型说了算"。
   M3 要验证的是这个，不是速度。

### 补记（2026-11-12）：`should_stop` 那次抽早了

原先我把它写成"最该抄的一处"，论据是"`max_steps` 从常数变成函数，改动量很小"。
**反驳我的一共三条，都成立：**

1. **`for` 并不阻止循环之后做事。** 我写过"`for` 物理上做不到再问一次模型"——错了，
   循环外面照样可以。`while` 的好处是动态续轮更好读，不是 `for` 缺这个能力。
2. **"end_turn 打赢护栏"这个说法本身有毛病。** 它预设两条规则在抢同一个时刻，
   于是才需要一张优先级表。更准的说法是：**预算允许最多发起 N 次调用，第 N 次也是
   合法调用；这次答完了，没有理由判失败。** 这不是消解冲突，是根本没有冲突。
3. **`decide(StopCandidate) -> bool` 那是个坏草图。** 调用方已经选好了 `reason` 再传进来，
   优先级其实在调用方手里；返回一个 `bool`，调用方还不知道最后报哪个原因。
   拿它论证"两边共用了停止语义"不成立。

还有一条更根本的：**我拿"是数据才当原子"这条判据，去反推"该不该有新类型"。**
判据是判断归类的尺子，不是决定"该不该有这个"的尺子。顺序反了。

**结论**：共用契约 **首先是两边遵守同一套明确、可测试的行为**，不一定要先共用一个函数。
M3 的第一个提交因此只做三件事（写明预算语义 + 三条测试），不换 `while`、不加新类型。

### 但这句话得说清楚：那是指下了的赌注，不是免费的正确答案

上面第 1–3 条我说服了自己，但有一笔账没算：

**一条规则写在一处，想漂也漂不了 —— 那是结构保证。**
**两份实现各配一套测试，理论上只要两边的新需求不完全一样，行为就会慢慢分叉**，
而测试发现不了"两边各自自洽但不一致"——它只能测"符不符合我这条测试"。

在 100 行的代码里这个赌注可以下，我同意下。但它是**赌注**，不是**免费的正确**。
写在这里，是为了两个月后（包括我们自己）别以为"共用契约"已经由代码保证了。
将来真发现两个引擎的停止行为悄悄分了叉，第一件事是回来读这一段。
