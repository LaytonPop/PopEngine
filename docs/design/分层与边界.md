# 分层与边界：原子、分子、框架

> 2026-11-11 对话整理。回答一个问题：**"框架、上下文、记忆、检索……这些东西到底怎么摆？"**
>
> 这份文件只讲**结构关系**，不讲怎么做。怎么做在各层的专项文档里。
> 判据：读完应该能回答"某个东西属于哪一层、它不该管谁"。

---

## 一、先给结论

三句话，后面全部是它们的展开：

1. **框架封装的不是智能，是接线。** 它让东西能拼起来，不决定什么时候停、该不该调工具。
2. **原子只有七个，PopEngine 已经全有了。** 缺的不是原子，是同一个原子的几种处理方式。
3. **"巨大"是层数错觉。** 五层，每层三五件事，加起来才显得吓人。

---

## 二、原子：七种数据

`types.py` 里的七个类，就是一次 run 里流动的全部。

```
ToolSpec   ──> 给模型看的工具说明书
ToolCall   ──> 模型要调哪个工具
ToolResult ──> 一次执行的结果（只活一瞬）
Message    ──> 一条对话消息（引擎唯一的持久状态）
LLMResponse──> 一次模型返回
StepEvent  ──> 一件发生过的事（只给人看）
RunResult  ──> 一次 run 的结局
```

**判断一个东西是不是原子，看它是不是"数据"。** 有行为的都不是原子，是变换器或循环。

三种变换器负责搬运原子：`to_wire` / `to_wire_tools`（出境）、`from_wire`（入境）。

---

## 三、分子：只有一个

原子怎么构成分子？答案朴素得让人失望：

```
Message 进 → LLMResponse 出
          → 有 ToolCall 就转成 ToolResult、再变 Message
          → 绕回去
```

**唯一的分子就是这个循环。** 其余一切都不是新分子，是给这个循环加配件。

这个判断很有用，因为它解释了为什么"加功能"通常不动 `loop.py` ——
功能都挂在循环的某几个点上，不改循环形状。

---

## 四、关键洞察：上下文、记忆、检索是同一个原子的三种处理

这一条想通了，那个"巨大"的感觉散一半。

```
Message 列表 ─┬─ 窗口与裁剪  ← 上下文管理
              ├─ 跨 run 存取 ← 记忆管理
              └─ 去外面找回来 ← 检索
```

| 叫法 | 实际在管 | 作用域 |
| --- | --- | --- |
| 上下文管理 | "这一次 run 里留多少" | 单次 run 内 |
| 记忆管理 | "下一次 run 还记得什么" | 跨 run |
| 检索 | "需要的时候去哪里捞" | 跨 run，按需 |

**所以"我只是个引擎"不是缺陷。** `Message` 已经够了，缺的是三种处理策略，不是新类型。

裁剪、压缩、摘要、落盘、加载、遗忘、向量检索——全是 `Message` 的不同处理，不是新原子。

---

## 五、五层

```
L0 原子 · 数据长什么样
L1 分子 · 一次 run
L2 机制 · 循环的配件
L3 编排 · 多个 run
L4 产品 · 给人用
```

| 层 | 内容 | PopEngine 现状 |
| --- | --- | --- |
| **L0** | 七个类型 + 三个变换器 | ✅ 完成 |
| **L1** | 循环、三个出口、事件 | ✅ 完成（M1/M2） |
| **L2** | 上下文管理、记忆、检索、权限、并发 | ❌ 0 / 5 |
| **L3** | 多 agent、graph、路由 | ⬜ M3 要做 |
| **L4** | TUI、会话持久化、审批、配置 | 🚧 只有 events（算半格 L2 可观测性） |

**"M3 的 graph 属于 L3"** —— 这一点要记住：在 L2 还没开工的时候先做 L3，是可以的，但要清楚自己在跳层。

## 六、框架：它到底封装了什么

拿 pi 的 `types.ts` 做证据（28 个 `export interface/type`），按性质分三类：

| 类别 | 数量 | 例子 |
| --- | --- | --- |
| **钩子与插槽** | **11** | `FinishTurn`、`PrepareRequest`、`BeforeToolCallResult`、`AgentToolUpdateCallback` |
| 配置与模式 | 4 | `ToolExecutionMode`、`ThinkingLevel`、`AgentLoopConfig` |
| 真正的数据与别名 | 13 | `AgentContext`、`AgentTool`、`AgentEvent` |

**一半以上不是数据，是"接口的形状"。** 这些类型描述的不是"有什么"，而是**"你可以在哪儿插进来"**。

所以框架的定位是：

| 你写引擎时要做 | 框架替你做的 |
| --- | --- |
| 想清楚数据长什么样 | 已经定好了 |
| 决定循环怎么转 | 已经转起来了 |
| **在关键节点留钩子** | **这就是它的主要价值** |
| 决定什么时候停 | **通常不管，要你自己给** |

最后一格最重要：**框架几乎从不替你决定"什么时候停"**，因为那需要业务判断。它只提供插槽。

### 用不用框架，差别在哪

- **不用**：每根线自己焊，慢，但坏了你知道在哪、为什么。
- **用**：三天出 demo，但出问题时中间隔着一层看不见的东西。

框架真正值钱的场景是**集成工作量**：接十种模型、二十种向量库、五种记忆后端。
PopEngine 只有一种模型、两个工具 —— 这时候上框架，等于为了接线方便放弃解释权。

**面试时这就是答案**："HTTP 是我自己发的"。
