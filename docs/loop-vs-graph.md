# loop vs graph：同任务同模型，各跑 3 次

> 写于 2026-11-26。数据来自 `scripts/run_compare.py`，原始账本在 `traces/compare/`
> （每 run 一份 `.json` 汇总 + 一份 `.events.jsonl`，三个数字可被任何人重算）。
> **指标定义归 [`design/引擎对比.md`](design/引擎对比.md) §七，本文只引用不重讲。**

---

## 一句话

**在这个任务上，graph 没有更快，也没有更稳；它只是把同一串模型调用切成了三段。**

---

## 数据

任务沿用 M2：给一个仓库路径，用 `list_dir` / `read_file` 看，输出固定五键 JSON。
同模型（`deepseek-flash`）、同仓库（本项目自身）、每引擎 3 次、**交替执行**。

### 主线表（`验收手册.md` d 轮要求的三列）

| 引擎  | `model_calls` | `total_ms` | `steps` |
| ----- | ------------- | ---------- | ------- |
| loop  | 5             | 5146       | 5       |
| graph | 6             | 7551       | 6       |

括号里是三次的原始值，表里填的是**中位数**：

```text
loop   model_calls 5 / 6 / 5      total_ms 5146 / 6542 / 4908
graph  model_calls 7 / 5 / 6      total_ms 8738 / 7551 / 10980
```

> ⚠️ **`steps` 这一列在第一行是 `model_calls` 的复制品，它不提供新信息。**
> 因为 `RunResult.steps` 的定义是"调用了几次模型"，而 loop 里每圈恰好一次模型调用。
> 这次两边都按同一个含义填（见 `graph/engine.py` 的 docstring），
> 所以两行都等于各自的 `model_calls`。
> 「结构做了几次决策」是另一个量，要用就得另起名字（`node_visits`），别借用 `steps` ——
> 否则同一字段名在两个引擎里表示不同东西，这张表就没法读。

其余观察值：

| 引擎  | 极差 | 五键通过 | 工具调用次数 |
| ----- | ---- | -------- | ------------ |
| loop  | 1    | 3/3      | 10 / 10 / 7  |
| graph | 2    | 3/3      | 5 / 2 / 3    |

`total_ms` 口径 **A：各事件 `duration_ms` 之和**，不是墙上时钟。
两者在这几跑里差 0.5–1ms（Python 开销可忽略），但口径必须写清 —— 混用会让这一列失去意义。

工具调用次数那一列最能说明问题，见下面第二条。


---

## 三件能解释的事

### 一、graph 更慢，因为它多花了模型调用

中位 6 次 vs 5 次，`total_ms` 中位 7551 vs 5146（+47%）。

这不是"graph 效率低"，是**三段式结构本身的代价**：`scan` 和 `read` 各要一次
"我说完了"的收尾调用，`report` 还要一次整合调用。loop 里这些都由同一次调用顺带完成。

一句话：**把活拆给三个 agent，就得付三次"你好"的钱。**

### 二、graph 用更少的工具调用，拿到同样的结果

工具：loop 平均 9 次（10/10/7），graph 平均 3.3 次（5/2/3）。

但两边五键都是 3/3 通过。**graph 用三分之一的工具调用做到了同样的事。**

这一条比时间那列有意思得多：loop 的模型自己决定"看够了"，于是反复 `list_dir`
扫了一堆它其实用不上的目录；graph 里 `scan` 的职责就只有"列一次根目录"，
它没有动机去扫第二遍。**约束省下的不是时间，是动作。**

### 三、`model_calls` 的方差没有被消灭 —— 我的预判错了

动笔前我断言（写在脚本 docstring 里）：

> router 是固定管线，不读模型写的东西，所以 `model_calls` 一定是常数（= 3 节点）。

**实测是 7 / 5 / 6，极差 2，比 loop 的 5 / 6 / 5 还大。**

原因：router 固定的是**走哪几个节点**，管不到**每个节点里模型问几次**。
节点内部还是一个完整的 `AgentLoop`，模型要 1 次还是 3 次工具，是它自己定的。

所以正确的说法是：

> **固定 router ⇒ 节点数固定 ⇒ 调用次数被夹在【节点数, Σ各节点预算】这个区间里。**
> 而那个区间的宽度是**配置给的**，不是测出来的。

这条推翻的是我自己写的判据，值得留着：**"结构决定停止"比"结构决定次数"弱得多。**

---

## 不能说的事

- **不能说 graph 更可预测。** 极差 2 > 1，方向还反了。要测这个，router 必须依赖
  模型写的 key（如 `enough: yes/no`），那才是"代码规则和模型的自觉在同一个位置竞争"。
- **不能说这次是纯引擎对比。** 两边的 prompt 不可能一样：loop 拿一个完整任务自己决定
  看什么；graph 的每段拿的是"只管这一步"的指令。**这是两种配置的对比。**
- **不能说 `total_ms` 差异是稳的。** n=3，而且同一个 prompt 连跑会命中 provider 的
  prefix cache（已用交替执行缓解，没有消除）。
- **不能说 graph「更省」。** 它省工具调用，但费模型调用。两个都是钱。

---

## 这一轮真正的收获（跟数字无关）

跑之前 graph **三次全部 `status="ok"`，而 `final_text` 是空串**。

原因链：`report` 节点 `max_steps=1`，但拿着整套工具 → 第一步就要 `list_dir`
→ 工具执行完、预算耗尽 → 子 run `failed/max_steps`、`final_text=""`
→ **图照样走完，报 ok**。

**一张"跑完了但什么都没产出"的图报 ok，就是假绿。** 它比报错危险：
报错会让人去看，假绿会让人拿着空结果继续往下走。

修法不是调任务，是让引擎认账：**只要有任何节点的子 run 没过，整图就是 `failed`，
并在 `error` 里点名是哪个节点、什么原因**（fail-closed；将来要"允许某节点失败、
由 router 绕开"，再显式加配置）。

这条和 `loop.py` 里那个**孤儿副作用**是同一个形状 —— 都是"预算掐掉的那一步，
结果没人看得到"。区别只在 loop 里留了 `test_l` 钉着，graph 里原来连钉子都没有。
现在有：`test_failed_subrun_makes_the_whole_graph_failed`。

## 下一步（按值钱程度排）

1. **让 router 读模型写的 key**（`scan` 写 `enough: yes/no`）。
   这是唯一能真正回答「结构决定停止 vs 模型决定停止」的形态，也是本次没能测的东西。
2. **`probe` 节点：让两边都能"多看一步"**。
   现在的 graph 是硬性三段，没有"发现材料不够就回去补"的能力 —— 那是它跟 loop
   最本质的差距，也是往届工作里 loop 唯一真正赢的地方。
3. n 提到 5，并给每次跑一个不同的无关措辞前缀，压掉 cache。
