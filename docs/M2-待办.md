# M2 待办

> 来源：M1 review 里发现、但**故意没在 M1 处理**的 4 件事。
> 现在不用读 —— M2 开工时我逐条讲，讲一条处理一条。

## 1. `stop_reason` 和 `tool_calls` 对不上时，谁来管？

现象（已用探针验证）：模型回 `stop_reason="tool_use"` 但一个 `tool_call` 都没给 →
loop 会空转到 `max_steps`，`error=None`，现场是几条一模一样的空 assistant 消息。

- 不是崩溃，是**烧完整个预算还不吭声**；M2 接真模型后每条都是真钱。
- 倾向方案：**在 provider 适配层校验**（`stop_reason` 和 `tool_calls` 来自同一个
  response，对不上就是适配层写错了），不要往 loop 里塞 `if`。
- 面试价值：这一条就是「为什么用 `stop_reason` 判断结束」那道题的代价。

## 2. tool 消息不要带 `name`

现在 `loop.py` 给 `role="tool"` 的消息塞了 `name=call.name`（内部调试有用）。
但 OpenAI 兼容接口的 tool 消息只认 `tool_call_id` + `content`，`name` 是老的
function-calling 字段。**写序列化时别发它。**

## 3. 两个小的

- `self.tools.specs()` 在循环里每圈重算。工具在一次 run 里不变，提到循环外一次即可。
- `max_steps` 终局的 `error` 是 `None`。机器读 `stop_reason` 够了，但 events.jsonl
  里"超预算"应该有句人话（`f"超过 max_steps={n} 步仍未结束"`）。

## 4. 真模型真跑，且留一次失败记录

一页纸的风险项：**假数据跑通 ≠ 真模型跑通**。M2 必须：
- 用 OpenAI 兼容接口真跑通一次；
- 故意留一次失败记录（网络错 / 参数错 / 工具返回模型看不懂），
  面试讲「怎么调试一个 agent」时用它。
