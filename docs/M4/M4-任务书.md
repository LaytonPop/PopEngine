## 一、第 1 关：循环三个薄参数 + 预算收尾

### 源码依据与我们的改编

1. **`before_model` 插槽**（照 `waku/loop/agent.py:109,125`）：
   - 签名：`before_model: Callable[[int, Sequence[Message]], Sequence[Message]] | None = None`
   - 只在 `step > 1` 调（第 1 步刚进来还没读过任何工具结果，不用压）；
   - **返回新序列、不原地改 `messages`**：发给 `provider.chat(list(chat_messages), ...)` 的是裁剪后的视图，而 `RunResult.messages` 保留完整现场供审计。
2. **`should_stop` 插槽**（照 `pi` `FinishTurn` + AgentScope `made_progress`）：
   - 签名：`should_stop: Callable[[int, LLMResponse, Sequence[Message]], str | None] | None = None`
   - **调用点必须在「append assistant 之后、执行工具之前」**（护栏必须在动作之前，否则带副作用的工具已经跑出去了）；
   - 返回非空字符串 `reason` 时当场中止：`RunStopReason` 新增 `"stopped"`，返回 `RunResult(status="failed", stop_reason="stopped", error=reason, ...)`。
3. **撞线禁工具**（改编自 `waku/loop/agent.py:165-209` 的 guardrail 2）：
   - `waku` 在 `max_iterations` 用完后用 `tool_choice="none"` 额外多问第 `N+1` 次来救回已查到的现场；
   - 但 PopEngine 的硬不变量是**「模型调用次数绝不超过 `max_steps`」**（`steps <= max_steps`）。
   - 所以我们的改编是：**当 `step == self.max_steps` 时（且 `max_steps > 1` 或本步为最后一步），传给 `provider.chat` 的 `tool_specs` 为 `[]`（空列表）**，逼模型在最后一步用已有材料就地作答！
   - 如果模型听话返回 `end_turn` → `status="ok"`，不再白扔前 `N-1` 步查到的资料，**孤儿副作用从成因上消失**（顺带从根上拔掉 M3 `report` 节点 `max_steps=1` 拿整套工具去 `list_dir` 导致 `final_text=""` 的病根）；
   - 如果模型不听话，没给工具说明书还硬返回 `tool_use` → **不执行任何工具**，直接返回 `status="failed", stop_reason="max_steps"`。
4. **改契约必改测试（单独一次提交）**：
   - 更新 `loop.py` docstring 的「预算语义」段；
   - 改写 `test_c` / `test_l`（旧语义是最后一步还照发 `tool_specs` 并执行工具留下孤儿副作用；新语义是最后一步禁工具，模型硬要工具也不执行）。

### 必过测试（`tests/test_hooks_loop.py`）

1. **零侵入回归**：不传新参数时，现有测试全绿。
2. **`before_model` 调用时机与视图隔离**：3 步 run 里只在 `step=2, 3` 被调用 2 次；`provider` 收到的是缩短后的消息，而 `RunResult.messages` 留着完整原文。
3. **`should_stop` 提前中止且工具零执行**：在第 2 步模型返回 `tool_use` 时触发 `should_stop`，断言 `stop_reason == "stopped"`，且该步请求的真实工具 **0 次执行**。
4. **撞线那次 `tool_specs == []`**：`max_steps=3`，前两步 `tool_use`，断言第 3 步 `provider.chat` 收到的 `tools` 参数为空列表 `[]`，模型正常答完返 `status="ok"`。
5. **不听话的模型硬要工具不执行**：第 `max_steps` 步 `tool_specs == []` 但假模型仍硬返 `tool_use`，断言工具 **0 次执行**，结局为 `status="failed", stop_reason="max_steps"`。

## 二、第 2 关：权限网关 + 两个真能干活的工具

### 源码依据

1. **能力标签放在 `Tool` 协议上，不放进 `ToolSpec`**：
   - `ToolSpec` 是发给模型看的 JSON Schema 说明书；`capability: Literal["readonly", "write", "exec"]` 是我们自己的安全元数据，写在 `Tool` 实现类上（`list_dir` / `read_file` 为 `"readonly"`，`write_file` 为 `"write"`，`run_command` 为 `"exec"`）。
2. **`src/pop_engine/permission.py`（照 `KamaClaude/core/permissions/policy.py:1-105`）**：
   - 4 层静态评估 `evaluate(tool_name, params, policy) -> PermissionDecision`（**顺序严禁调换**）：
     - **Tier 1**：`deny_patterns`（命中直接 `DENY`）
     - **Tier 2**：`OUTSIDE_CWD_HEURISTICS`（6 条正则抓绝对路径、`~`、`..`、`$HOME`、`$PWD`、`cd` —— 命中**强制 `ASK`，不可被 Tier 3 `allow_patterns` 绕过**！）
     - **Tier 3**：`allow_patterns`（命中 `ALLOW`）
     - **Tier 4**：工具默认策略（`readonly` 工具默认 `ALLOW`，`write`/`exec` 及未知工具默认 `ASK`）。
   - **`PermissionGate` 装饰器**：
     - 包装 `ToolRegistry`，对外提供一模一样的 `specs()` 与 `invoke(call: ToolCall) -> ToolResult`；
     - 评估为 `ALLOW` → 委派 `registry.invoke(call)`；
     - 评估为 `ASK` → 调 `approver(call) -> bool`（未配 `approver` 时等同拒绝）；
     - 评估为 `DENY` 或 `approver` 拒绝 → 直接返回 `ToolResult(tool_call_id=call.id, content="权限拒绝: ...", is_error=True)`，**被拒工具执行次数为 0**。
     - **不抄** `KamaClaude` 的 `storage.py` 跨进程持久化与 `asyncio.Future` 双进程挂起。
3. **`src/pop_engine/tools/builtin.py` 新增两个同步工具（照 `KamaClaude/core/tools/builtin/write_file.py, bash.py`，改同步）**：
   - `write_file(path, content)`：锁 `root` 目录（`..` 或越界直接拒绝，零字节落盘）、1MB（`1024 * 1024` bytes）上限、自动 `parent.mkdir(parents=True, exist_ok=True)`。
   - `run_command(command, timeout=60)`：用同步 `subprocess.run`（**不抄 KamaClaude 的 asyncio**），锁 `cwd=root`，`timeout` 范围 1–120 秒（默认 60），合并 stdout + stderr，超 64KB 截断附 `\n[truncated]`，超时返 `"[timeout after {timeout}s]"`（`is_error=True`），非零退出码返 `"[exit {code}]\n{output}"`（`is_error=True`）。

### 必过测试（`tests/test_permission.py`）

1. **表驱动 4 层评估**：特别是 Tier 2 `OUTSIDE_CWD_HEURISTICS`（如 `cat ../secret`、`cd /tmp`）在 `allow_patterns` 已配白名单时仍强制返回 `ASK`。
2. **拒绝时工具零执行**：被 `DENY` 或 `approver` 拒掉时，底层 `Tool.run` 调用计数为 **0**。
3. **拒绝后模型自愈收尾**：模型第 1 步写文件被拒 → 收到 `is_error=True` 的权限拒绝 `ToolResult` → 第 2 步改口正常 `end_turn`。
4. **`write_file` 正向与 `..` 越界零字节落盘 + 1MB 超限拦截**。
5. **`run_command` 正向、非零退出带 `[exit N]`、超时不挂死**。
6. **`approver` 回调放行与拒绝**。

## 三、第 3 关：会话持久化 + 真·断点恢复

### 源码依据与我们的升级

1. **为什么 `KamaClaude` 做不到「第 3 步被 kill、从第 4 步续跑」【读源码核实】**：
   - `KamaClaude/core/runner.py:110` 在 run 开始前读历史，`:193` 在整次 `loop.run()` **全部结束之后**才 `store.append_messages()`。如果进程在第 3 步被 kill，前 3 步一条都没落盘！
2. **我们的真·断点落盘设计**：
   - `AgentLoop.__init__` 增加 `on_message: Callable[[Message], None] | None = None`；
   - 在 `loop.py` 里 **user / assistant / tool 三处 `messages.append(...)` 之后立刻调用 `on_message(msg)`**（每一步实时追加写进 `thread.jsonl`）；
   - `AgentLoop.run(prompt: str, *, history: Sequence[Message] = ()) -> RunResult` 支持传入已恢复的历史消息。
3. **`src/pop_engine/session.py`**：
   - `message_to_dict(msg)` / `message_from_dict(d)`：**无损往返**（完整保住 `tool_calls` 元组里的 `ToolCall` 与 `raw_arguments`）。
   - `SessionStore`：追加写 `thread.jsonl`、读写 `meta.json`，读取时遇到半截损坏的 JSON 坏行跳过不崩（照 `KamaClaude/core/session/store.py:89-93`）。
   - **孤儿 `tool_use` 修复：补齐优先、回滚兜底**（刻意优于 `KamaClaude store.py:109` 的一刀切回滚）：
     - 当进程在 `assistant(tool_calls=[c1, c2])` 跑完 `c1`、正在跑 `c2` 时被 kill，`thread.jsonl` 里有 `assistant` 和 `c1` 的结果，缺 `c2` 的回执。
     - 如果一刀切回滚把 `assistant` 和 `c1` 全删掉，模型不知道 `c1` 的副作用已经发生了，重跑会再执行一遍 `c1`！
     - 所以我们给所有「有请求无回执」的 `tool_call_id` **补齐一条合成回执**（`role="tool"`, `content="[系统恢复：上次运行在此工具完成前中断，结果未知，副作用可能已发生]"`）；只在末尾 `assistant` 消息本身损坏不可读时才回滚到 `last_balanced`。

### 必过测试（`tests/test_session.py`）

1. **`Message` 全形态无损往返**（含多 `ToolCall`、含 `raw_arguments`、含 `role="tool"`）。
2. **`on_message` 实时触发次数与顺序**：user → assistant(tool_calls) → tool → assistant(end_turn) 逐条实时落盘。
3. **跨实例多轮续聊**：实例 1 跑完第一轮落盘，实例 2 读 `SessionStore` 作为 `history` 跑第二轮。
4. **残缺历史愈合后 `to_wire` 100% 合法**：1 拖 2 工具只落盘了 1 个 `tool` 结果，愈合后补齐第 2 个合成回执，`openai_compat.to_wire()` 零报错。
5. **第 3 步被 kill 续跑后，前 3 步已执行的工具绝不重跑第二遍**。
6. **`thread.jsonl` 末尾混入半截坏 JSON 行时跳过不崩**。

## 四、第 4 关：两级压缩（一级免费，二级才花钱）

### 源码依据

1. **第一级 `shrink_seen`（免费，照 `waku/loop/trim.py:1-53`）**：
   - 常量：`LONG_CHARS = 4000`、`KEEP_CHARS = 2000`；
   - 扫描**最新一轮之前**（`messages[:-1]` 或最新一批 `tool` 结果之前）模型已经读过的 `role == "tool"` 消息；
   - 若 `len(msg.content) > LONG_CHARS`，截留 `msg.content[:KEEP_CHARS] + note`；
   - **最新一轮刚产出的 `tool` 消息一字不碰**；截过一次后长度 `< LONG_CHARS`，以后轮次永远不再变动（100% 幂等，保 Prefix Cache），且不改消息条数与 `tool_call_id`。
2. **第二级六段式交接摘要（超水位才花钱，照 `KamaClaude/core/compact/compactor.py:17-155`）**：
   - 当一级 `shrink_seen` 后估算 token 仍超水位阈值时，用 `_COMPACT_PROMPT`（六段：Original Goal / Completed Steps / Key Constraints & Discoveries / Current File State / Remaining TODOs / Critical Data —— 其中 `Completed Steps` 明确记录已执行的副作用）调一次 `provider.chat`；
   - 将被压缩的历史段替换为 `[Message(role="user", content=summary), Message(role="assistant", content="Understood, I'll continue from this summary.")]` + 保留尾部完整配平的回合单元；
   - **切分边界铁律**：切分点绝不能落在 `assistant(tool_calls)` 与其对应的 `role="tool"` 消息之间；
   - **最后一步（`step == max_steps` 禁工具步）不触发二级摘要**（省掉最后一步前无谓的额外 LLM 调用）；
   - `EventKind` 新增 `"compact"`，记录压缩前后 token 数；若摘要 LLM 调用抛异常或返空串，优雅降级保留原消息继续，不中断主任务。

### 必过测试（`tests/test_compact.py`）

1. **未超线时返回原消息序列，零 LLM 摘要调用**。
2. **一级 `shrink_seen` 保配对、不碰最新一轮 `tool` 结果、连续调用幂等**。
3. **二级六段摘要超水位触发 + 产出 `kind="compact"` 事件**。
4. **切分位置撞在「1 拖 3 工具调用」中间时自动对齐回合边界，绝不破 `to_wire` 配对**。
5. **摘要调用抛异常时优雅降级，主循环继续跑完**。
6. **端到端挂载进 `AgentLoop(before_model=...)` 连续读 6 个大文件一次跑通**。
