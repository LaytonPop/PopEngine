# 协作约定

> 这份文档管的是**怎么提交**，不是**写什么**。
> 改规则只改这一页；改完在 commit 里说一声为什么改。
>
> 建立于 2026-11-10。项目：PopEngine（仓库 `LaytonPop/PopEngine`）。

---

## 一、分支：谁做的活，进谁的分支

| 谁 | 分支前缀 | 例子 |
| --- | --- | --- |
| **Alma**（我） | `alma/` | `alma/events`、`alma/conventions`、`alma/m3-graph` |
| **Pop**（你） | `Pop/` | `Pop/m3-graph`、`Pop/readme`、`Pop/实验` |

### ⚠️ 一个技术事实：不能直接叫 `alma/`

git 的分支名**不允许以 `/` 结尾**。所以 `alma/`、`Pop/` 这两个字面量是非法的：

```console
$ git check-ref-format --branch "alma/"
❌ 非法
$ git check-ref-format --branch "alma/loop"
✅ 合法
```

规则落地成：**`alma/<主题>` 和 `Pop/<主题>`**。
主题用短横线小写英文（`m3-graph`），不用中文——分支名会在 URL、命令行、CI 里出现，
中文要转义，麻烦。

### 为什么分两个前缀

不是为了分工好看，是三条实在的理由：

1. **署名**：`git branch` 一眼能看出这行代码是谁动的，不用翻 `git log`
2. **可以各自乱来**：我改一半、你改一半，互不阻塞
3. **出错好回退**：我这一支写崩了，直接删，不污染主线

### 合并

```
alma/xxx ──┐
           ├──> main
Pop/xxx ───┘
```

- **默认：合并前先问。** 我做完一支会告诉你结论和验证结果，你点头我再合。
- 紧急/琐碎（错别字、一行修）可以直推 `main`，但要在 commit 里说明为什么跳过了分支。
- **合并走 PR 还是本地 `merge`，二选一，不要两边都做。** 见下面「谁先动的手」。
- 合并用 `--no-ff`，保留分支形状——将来 `git log --graph` 能看出"这段是谁做的"：

```bash
git checkout main
git merge --no-ff alma/events -m "merge: alma/events → main"
```

### 谁先动的手（2026-11-10 加，因为真撞了一次）

第一次按约定走的时候撞了一回：我本地 `merge --no-ff` 合完准备推，`push` 被拒——
因为**同一时刻 Pop 在 GitHub 上开了 PR #1 把同一个分支合了**。

两边都做了"合并"这个动作，结果是我本地多了一个没人知道的 merge commit。

这不怪谁，是**缺一条约定**：合并这件事只能有一个执行者。

所以补三条：

**1. 推之前先 `fetch`，别用 `push` 去撞墙**

```bash
git fetch origin
git status -sb          # 看有没有 behind / diverged
```

被拒之后再 `fetch` 是补救；先 `fetch` 是习惯。差别在于：
前者你已经在解释一个错误，后者你根本没制造它。

**2. 撞上了怎么办：先比树，再决定能不能丢**

远端已经合过、我本地也合过一次，**千万不要直接 `pull`**（会造出"合并的合并"），
也不要直接 `reset`（万一本地那次合并带了远端没有的东西，就真丢了）。

先比内容：

```bash
git rev-parse main^{tree}          # 本地 main 指向的树
git rev-parse origin/main^{tree}   # 远端 main 指向的树
```

| 结果 | 含义 | 怎么做 |
| --- | --- | --- |
| **两个哈希相同** | 同一批改动，只是入口不同 | 可以 `git reset --hard origin/main`，本地那次合并可以丢 |
| **哈希不同** | 两边各自有东西 | 不能硬重置。`git pull --rebase` 或人工挑，内容和历史都要保 |

**只有树相同才允许硬重置。** 这条不分场合——`reset --hard` 会静默丢掉工作区里
未提交的改动，先跑一次 `git status` 看清楚。

**3. 默认让 Pop 合**

约定里写"合并前先问"，但"问"和"合"之间有时间差，正好够两边同时动手。
更省事的做法：**我把分支推上去、报告结论和地址，合这个动作交给 Pop**。
我这边就停在"已推送，等合并"，不本地合。

真需要我合的时候（你不在、或者急着继续），我会明确说一句"我直接合了"，
不会默默两边都做。

## 二、提交信息：`type(scope): 中文说清做了什么`

现有历史已经是这个形状，本约定只是把它写下来：

```
feat(m2): StepEvent 事件系统 —— loop 埋点 + RunResult.events
fix(scripts): --trace 改成真参数，事件落盘 jsonl
docs(m2): c 轮事件设计 + 验收手册实测 + 证据留档
refactor: 项目改名 PopEngine，包名 pop_engine
chore: .gitignore 忽略 .tmp/
```

### type 表（只认这六个）

| type | 什么时候用 |
| --- | --- |
| `feat` | 新增能力，用户/调用方能感知 |
| `fix` | 修 bug。**正文要写清"修之前会怎样"** |
| `refactor` | 不改行为的结构调整（改名、拆文件、提取函数） |
| `docs` | 只有 `.md` 变化 |
| `test` | 只有测试变化 |
| `chore` | 配置、依赖、`.gitignore` 这类杂活 |

**不新增 type。** 想要 `perf`、`style`、`ci` 的时候先问：这个仓库有性能指标吗？有 CI 吗？
没有就是 `feat` 或 `chore`。type 越多，越没人用对。

### scope 是可选的，写"哪一块"

`(m2)` `(scripts)` `(diagrams)` `(types)`。**不要写文件名**（`(loop.py)`），
文件会改名，模块不会。

### 标题的规矩

- **中文**，因为笔记和文档都是中文，中英混排读者要来回切
- 不超过 **50 字**，一行说完
- **说做了什么，不说"更新"、"修改"**："改了 A 让 B 不再 C" 好过 "优化代码"

### 正文：写"为什么"，不写"改了什么"

`git diff` 已经能看出改了什么，正文写它看不出来的东西：

```
fix(m2): unknown 兜底 —— 不让它掉进工具分支空转

finish_reason 认不出时 from_wire 返回 unknown，它不违反
「tool_use ⟺ calls>0」那条等价，所以校验合法放行，然后掉进
工具分支空转：tool_calls 为空 → for 一次不跑 → 同一响应绕到
max_steps，error 还是 None。

修前实测 steps=8 / 模型调用 8 次 / error=None；
修后 steps=1 / 模型调用 1 次 / error 写清原因。

破了一次「不许改 loop.py」的铁律 —— 映射表 §二·6 自己把责任
派给了 loop，边界划漏了一格，不是接线问题。
```

三件事值得进正文：**改之前的症状、为什么选这个方案（而不是另一个）、破了什么规则和为什么值得破**。

## 三、一次提交 = 一件事

判据很简单：**能不能用一句话说完，且这句话里没有"并且"。**

```diff
✅ 分开
  fix(scripts): --trace 改成真参数
  docs(m2):    c 轮事件设计 + 实测

❌ 混在一起
  feat: 加事件系统 + 修 --trace + 更新文档
```

第三个反例的问题不在好不好看，在于**回滚**：将来发现 `--trace` 那个改法不对，
想单独撤回它，混在一起就只能整个回退，把事件系统也一起带走。

连续几次"我顺手把这个也改了"之后，`git bisect` 就废了。

## 四、提交前必做

### 1. 三件套全绿

```bash
uv run python -m pytest -q
uv run python -m ruff check src scripts tests
uv run python -m mypy src scripts tests
```

**红了不许提交。** 哪怕"这个红跟我的改动无关"——先弄清楚它为什么红，
因为下一眼看到它的人只有 `git log`。

### 2. 扫一遍要提交的东西

```bash
git status
git diff --staged
```

**逐行看过再 commit。** 不是信不过工具，是"我到底改了什么"这件事，
只有看一眼才真的知道。经常会有意外：调试用的 `print`、临时改的路径、注释掉的代码。

### 3. 红线检查

```bash
git grep -nE "sk-[A-Za-z0-9]{16,}|gho_[A-Za-z0-9]{20,}|ghp_[A-Za-z0-9]{20,}"
```

**期望：没有输出。**

## 五、绝不提交的东西

| 东西 | 为什么 | 挡住它的是 |
| --- | --- | --- |
| `.env` | 里面有真 key | `.gitignore` |
| `traces/*.jsonl` | 跑一次生一次，每次内容都不同 | `.gitignore` |
| `.tmp/` | 草稿，随时可删 | `.gitignore` |
| `__pycache__/`、`.venv/` | 机器生成的，跟代码无关 | `.gitignore` |
| 任何 `print` 调试残留 | 会污染正常输出 | 提交前 `git diff` 看一眼 |

**要留的证据不放进 `traces/`，复制到 `docs/evidence/`。** 那边有 README 说明它为什么值得留。

> 一条更硬的原则：**凭据永远不进仓库，一次也不行。**
> 就算"马上就删"，它也已经在 `git log` 里了——删文件不等于删历史，
> 得改写历史（`filter-repo`）才干净，而推过的仓库改写历史要 force push，
> 会打掉别人的分支。所以真正的防线是**不让它进来**，不是进来之后删掉。

## 六、文档之间谁说了算

| 想知道 | 看 |
| --- | --- |
| **现在该做什么** | `docs/TODO.md` ← 唯一待办入口 |
| **怎么提交** | 本文件 |
| **怎么验收** | `docs/验收手册.md` |
| **某个设计为什么这样** | 对应的任务书 / 映射表 / 事件设计 |
| **已经跑出来的实物** | `docs/evidence/` |

**冲突时：TODO.md 管"做什么"，本文件管"怎么提交"，其余都是解释。**
解释和实现不一致时，以实现为准，然后**去改解释**——留着一份和代码相反的文档，
比没有文档更害人（这条已经踩过两次：`types.py` 的 docstring、`loop.py` 的文件头）。

## 七、Coding agent 的边界（给我自己）

- **改代码前先说清改哪几个文件**，不要一口气重写一大片
- **不擅自改测试断言**。红了先解释为什么红；真要改断言，单独一次提交并说明理由
- **不擅自扩范围**。"顺手优化一下"是范围蔓延的入口
- **不确定就停**。停下来问，比写错一百行便宜
