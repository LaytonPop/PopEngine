### ④ 反向验收：四条防线 + 一条网络

把这段整块贴进 PowerShell 跑（这是唯一一段需要直接碰 Python 的，其他都是敲脚本）：

```powershell
& $py -c @"
from kama_engine.tools import ToolRegistry
from kama_engine.tools.builtin import ListDirTool, ReadFileTool
from kama_engine.types import ToolCall
reg = ToolRegistry([ListDirTool('.'), ReadFileTool('.')])
for name, kw, raw in [
    ('read_file', {'path': '../etc/passwd'}, None),
    ('read_file', {'path': 'C:/Windows/win.ini'}, None),
    ('read_file', {}, None),
    ('nope', {}, None),
    ('read_file', {}, '{\"path\": \"a.p'),
]:
    r = reg.invoke(ToolCall(id='x', name=name, arguments=kw, raw_arguments=raw))
    print(name, kw, 'raw=', bool(raw), '-> is_error=', r.is_error)
"@
```

**通过标准**：五行全部 `is_error=True`，且错误信息分别说得清是哪种错：

| 输入                          | 应该报                   |
| ----------------------------- | ------------------------ |
| `../etc/passwd`             | 路径越界                 |
| `C:/Windows/win.ini`        | 不允许绝对路径           |
| 缺 `path`                   | 缺少参数 path            |
| 工具名 `nope`               | 未知工具                 |
| `raw_arguments` 是半截 JSON | 参数不是合法的 JSON 对象 |

**为什么这五行重要**：这五个都是"模型可能给、程序必须接住"的输入。任何一行变成 `is_error=False` 或者抛异常把 loop 炸掉，就等于模型能一句话让你的 agent 崩。

### 反向验收（关键）—— 四条，每条都能整段贴进 PowerShell

> 这一段是**动手教材**。四项都是同一个套路，照着走就行：
>
> | 步骤                   | 干什么                             |
> | ---------------------- | ---------------------------------- |
> | **要造什么**     | 一句话说清要伪造哪种坏输入         |
> | **怎么造**       | 一整段可复制的命令，不用自己补     |
> | **应该看到什么** | 逐行的期望输出，附「这一行怎么读」 |
> | **为什么**       | 这一步在防哪种真事故               |
>
> 四条互不依赖，可以单独跑。① ② 是造坏输入验已有防线，③ 是回归，④ 是**给测试补一条**（还没做）。

#### ① `stop_reason` 与 `tool_calls` 自相矛盾 —— 造两个坏响应，看是否当场止损

**要造什么**：同一个 response 里，结束原因和工具调用列表对不上。两种写法各造一次：

| 造的假响应                                            | 期望                                 |
| ----------------------------------------------------- | ------------------------------------ |
| `finish_reason="tool_calls"` 但 `tool_calls` 为空 | 当场报错（不是空转到 `max_steps`） |
| `finish_reason="stop"` 但带 `tool_calls`          | 当场报错（不是把工具请求丢了当答完） |

**怎么造**：整段贴进 PowerShell。原理是拿真 fixture 改一个字段，再包一个假网关，
逼着 `provider.chat()` 里那层 `from_wire` 去解析它 —— 校验在哪一层，坏输入就得从哪一层进去。

```powershell
& $py -c @"
import json
from pathlib import Path
from kama_engine.openai_compat import from_wire
from kama_engine.loop import AgentLoop
from kama_engine.tools import ToolRegistry
from tests.fakes import AddTool

base = json.loads(Path('tests/fixtures/deepseek_tool_calls.json').read_text(encoding='utf-8'))

class Gateway:
    def __init__(self, reason, drop_calls):
        self.n = 0
        d = json.loads(json.dumps(base))
        d['choices'][0]['finish_reason'] = reason
        if drop_calls:
            d['choices'][0]['message'].pop('tool_calls', None)
        self.d = d
    def chat(self, messages, tools):
        self.n += 1
        return from_wire(self.d)

for label, reason, drop in [
    ('A: tool_calls 但无调用', 'tool_calls', True),
    ('B: 带调用却说 stop',     'stop',       False),
]:
    p = Gateway(reason, drop)
    r = AgentLoop(p, ToolRegistry([AddTool()]), max_steps=8).run('hi')
    print('%s  status=%s stop=%s steps=%s 模型调用=%d' % (label, r.status, r.stop_reason, r.steps, p.n))
    print('    error=%s' % r.error)
"@
```

**应该看到什么**（2026-11-06 实测）：

```
A: tool_calls 但无调用  status=failed stop=error steps=1 模型调用=1
    error=ValueError:finish_reason=tool_calls 但 tool_calls 为空：stop_reason 与调用列表自相矛盾
B: 带调用却说 stop     status=failed stop=error steps=1 模型调用=1
    error=ValueError:带了 1 个 tool_calls，finish_reason 却是 'stop'：这种响应会让 loop 以为已经答完，把调用静默丢掉
```

这一行怎么读：

- `status=failed` —— 收场了，没崩。
- `stop=error` —— 走的是 loop 的异常分支，不是 `max_steps`。
- **`steps=1` 和 `模型调用=1` 是最关键的两个数**：一次调用就止损，预算没被烧。
- `error=` 后面是 `from_wire` 抛的那句话，原样落到 `RunResult` 里。

**为什么**：这两种都是真模型抽风时会出现的形态。a 轮之前的代码是**静默的** ——
第一种会空转到 `max_steps`，第二种会把调用丢掉当答完。现在两种都在转换层当场拦住。

> 顺便验收了一个承诺：映射表 §七 说「放在转换层，它自动落进 loop 既有的失败路径，
> 预算不会被烧完」。这个脚本就是在那句话上做实测 —— **`steps=1` 就是证据**。

留着它是因为**面试时这张表能直接画在白板上**——「9 组符合预期，1 组是洞」比嘴上说清楚。

#### ② `unknown` + 无调用 —— 同一套办法，换一个字段（**这条还没修**）

**要造什么**：`finish_reason` 换成 `length`（被截断），并且**不带** `tool_calls`。

**怎么造**：跟 ① 一模一样，只把 `reason` 和 `drop` 换掉：

```

八次真钱调用，`error` 是 `None`，现场只有几条一模一样的空 assistant 消息 ——

**修之后应该长这样**（2026-11-07 已修复并实测）：

status=failed stop=error steps=1 error='模型以未建模的原因停下（stop_reason=unknown），第 1 步中止' 模型调用=1
```

一次调用就止损，`error` 里说清了是哪种原因、在第几步停的。

> 这一格现在必须**亲手跑出来**才算验完。如果跑出 `steps=8`，说明兜底没生效
> （最常见的原因：`if` 写在了 `for` 循环后面而不是前面）。

**为什么**：① 和 ② 合起来才说清 b 轮的完整要求。① 是「同一个 response 自相矛盾」，
② 是「模型合法地以我们没建模的原因停下」。前者该在转换层拒绝，

> **为什么这里必须改 `loop.py`**：映射表 §二 · 6（`finish_reason`）定分工时写着「转换层产出这个值；loop 只读懂，不做二次判断」，
> 并明确警告「**别让 `unknown` 掉进 else 变成空转**」——责任在 loop 这一侧，而 loop 里没有那个兜底。
> §七 补的是另一条等价（`tool_use` ⟺ `calls`），没补这条口子。
> 两个 TODO 各自都做对了，**接缝处漏了**。所以修法只能是给 loop 补兜底，而不是让转换层多抛一种错。

#### ④ `to_wire_tools` 的双 spec 顺序断言 —— 给测试补一条（**已做，2026-11-07**）

**要造什么**：一条**新的**测试，一次传两个 spec 进 `to_wire_tools`，验「两个都留下 + 顺序就是传入顺序」。

**为什么必须两个**：`to_wire_tools` 现在有三条测试，**全都只传一个 spec**。
只传一个的话，「顺序错乱」和「只转第一个/最后一个」这两种写法**永远是绿的**——
因为一个元素的列表没有顺序可言。这和 `test_from_wire_parallel_tool_calls_keeps_every_call`
的注释里写的盲区是同一种：

> 真实响应里只有一个调用，所以「只转换最后一个」这种差一层的写法在 fixture 上永远是绿的。

`to_wire_tools` 的处境完全一样：**真实任务就是两个工具**（`list_dir` + `read_file`）。

**怎么造**：先看**写错的样子**（这一步很重要，知道会怎么错才知道断言在防什么）。

最常见的错法是「定义了第二个 spec，但调用时忘了传」：

```python
# ✗ 错法：spec2 定义了，但 to_wire_tools([spec]) 只传了一个
spec = ToolSpec(name="read_file", description="读文件", parameters={"type": "object"})
spec2 = ToolSpec(name="list_dir", description="列目录", parameters={"type": "object"})

wire = to_wire_tools([spec])          # ← spec2 根本没进去
assert len(wire) == 1                 # ← 断言也只验一个，测试还是绿的
```

**这种写法有三个症状，任何一个都能把你拦下来**：

| 症状                                         | 怎么发现                                               |
| -------------------------------------------- | ------------------------------------------------------ |
| 测试还是绿的，但什么都没多验                 | 数一下 `to_wire_tools([...])` 方括号里到底有几个元素 |
| `ruff` 报 `F841 Unused variable "spec2"` | 跑 a 轮 ① 的静态四连，第二行就报                      |
| `mypy` / 编辑器把 `spec2` 灰掉           | 变量声明了没引用，IDE 会提示                           |

实测这条：`to_wire_tools([spec])` 产出 **1** 条，`to_wire_tools([spec, spec2])` 产出 **2** 条。
所以只传一个的测试，对「第二个去哪了」这个问题**完全没有约束力**。

正确写法 —— 新开一条测试，别动原来那条。原来的 `test_to_wire_tools_wraps_in_function_object`
钉的是「单条的精确形状」，职责单一；把两个 spec 塞进去会让那条断言变成三倍长，
出了问题也看不清是谁的锅。**一条测试只回答一个问题**：

```python
def test_to_wire_tools_keeps_two_specs_in_order() -> None:
    """两个 spec 都要留下，且顺序就是传入顺序。

    现有三条测试全都只传一个 spec —— 一个元素的列表没有顺序可言，
    所以「顺序错乱」和「只转第一个/最后一个」这两种写法在它们面前永远是绿的。
    这和 test_from_wire_parallel_tool_calls_keeps_every_call 是同一种盲区：
    真实任务就是两个工具，测试就该给两个。

    名字故意选成 read_file 在前、list_dir 在后 —— 按字母序排的话
    list_dir 该在前。所以这条断言同时排除了「不小心按名字排序」的实现。
    """
    # Arrange：两个 spec，属性各有区分度，便于定位是哪一条串了。
    first = ToolSpec(name="read_file", description="读一个文本文件", parameters={"type": "object", "properties": {"path": {"type": "string"}}})
    second = ToolSpec(name="list_dir", description="列一层目录", parameters={"type": "object", "properties": {"path": {"type": "string"}}, "required": ["path"]})

    # Act
    wire = to_wire_tools([first, second])

    # Assert：整份全等 —— 条数、顺序、包装层、parameters 仍是 dict，一次全覆盖。
    assert wire == [
        {
            "type": "function",
            "function": {
                "name": "read_file",
                "description": "读一个文本文件",
                "parameters": {"type": "object", "properties": {"path": {"type": "string"}}},
            },
        },
        {
            "type": "function",
            "function": {
                "name": "list_dir",
                "description": "列一层目录",
                "parameters": {"type": "object", "properties": {"path": {"type": "string"}}, "required": ["path"]},
            },
        },
    ]
```

**为什么用整份全等而不是拆成几条断言**：和现有那条 `wraps_in_function_object` 保持一致。
全等一次盖住「条数 / 顺序 / 外层包装 / `parameters` 没被 dumps / 没夹带内部字段」五件事，
而且**反过来传**（`[second, first]`）会立刻失败 —— 这才叫顺序断言。
